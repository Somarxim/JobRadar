## 改动内容

W3-3 上线后用户实测反馈的两个问题修复：

1. **牛客岗位链接全部失效**（数据质量事故）
   - 根因：`NowcoderSearchParser.DETAIL_URL` 写的 `https://www.nowcoder.com/jobs/{id}`——
     该地址返回 HTTP 200 但渲染牛客首页（SPA 前端路由不命中的**软 404**）；
     真实详情页是 `/jobs/detail/{id}`（页面 title 含岗位名、canonical 自指证实）。
   - 修复：DETAIL_URL 改为 `/jobs/detail/`；两处测试断言同步；
     dev 库存量 169 条爬虫源 URL 批量 UPDATE 修正（插件录入的正确数据未动）。
2. **推荐区展示模型不符预期**
   - 用户预期「一炉 5 条、批批替换」，原实现把已 accept/ignore 的条目留在列表里
     （降透明度展示），重跑后新旧混杂。
   - 修复：`GET /recommendations/today` 只回 PENDING（已处理记录留库供质量评估，
     不再展示）；前端反馈成功后条目立即消失；移除降透明度展示逻辑。
   - 「立即推荐」反馈强化：运行期间推荐区显示占位提示（说明 LLM 精评约 1~2 分钟），
     完成后整表刷新 + toast 汇报漏斗数字。

## 改动原因

用户实测反馈：链接点进去全是失效页；推荐刷新后新旧混在一起、触发反馈不明显。
推荐的产品语义确认为「每日一炉 Top 5，处理一条少一条」，而非「流水账+状态标记」。

## 技术概念卡

### SPA 软 404：HTTP 200 ≠ 页面有效
- 是什么：单页应用的服务端对任意路径都返回 200 + 应用壳，路由不命中由前端 JS
  渲染成首页/404 页——curl 看到 200 不代表链接有效。
- 项目里哪里用了：牛客 `/jobs/{id}`（软 404 到首页）vs `/jobs/detail/{id}`（真实详情页）。
  W3-2 验证时只看了状态码，属于「验证方式错误」而非「实现笔误」。
- 面试可能追问：爬虫数据质量怎么保证？→ 抓取字段要做内容级校验（title 非空/页面
  title 含关键词/canonical 自指），不能只做传输级校验（状态码）；存量数据要有修复
  预案（本次 SQL 批量 UPDATE，dedupe_hash 不含 URL 所以改链接不产生重复）。

### 产品语义决定查询语义
- 「推荐」从「流水账 + 状态」改为「一炉一批、只看待处理」后，接口层直接过滤
  PENDING（DB 侧），而不是把全部数据丢给前端自己筛——展示规则是领域规则，
   belongs to 后端契约。
