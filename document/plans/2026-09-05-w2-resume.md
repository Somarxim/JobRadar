## 改动内容

W2 第三切片：简历上传 + PDFBox 解析 + ResumeProfile 结构化档案（匹配 Agent 的数据源前置）。

1. **契约实现**（api-design.md §resumes）：`POST /resumes`（multipart PDF）、`GET /resumes`、`GET /resumes/{id}`、`POST /resumes/{id}/reparse`、`PATCH /resumes/{id}/default`
2. **core 层**：
   - `ParsedResume` record（ResumeProfile schema：education 含 is985/is211 推断、experiences 分 internship/project/competition/research、skills/awards/targets/summary）
   - `LlmService.parseResume(text)`：复用 parse 模型（DeepSeek），task=`resume_parse` 记账
   - `ResumeService`：**非注解组件**（构造参数含配置值 resumeDir，与 LlmService 同模式由 app 层 `ResumeConfig` 显式 @Bean）；上传流程 = 校验（空/10MB 上限/PDF 魔数）→ UUID 文件名落盘 `~/.jobradar/resumes/` → PDFBox 抽文本 → LLM 结构化 → JSONB 落库；**解析失败不阻断上传**（原件已存，pending 可 reparse）；首份自动默认
3. **app 层**：`ResumeController`（multipart 拆包在 Controller，core 只收 byte[]）；`JobRadarProperties` 增加 `storage.resume-dir`；`application.yml` 增加 multipart 上限 10MB（**Spring 默认 1MB 会误拒正常简历**）；`GlobalExceptionHandler` 增加 `MaxUploadSizeExceededException` → 400 契约错误体
4. **前端**：`/resumes` 页面（上传 + 卡片列表 + 默认/解析状态徽章）+ AI 档案确认弹窗（意向/教育含 985·211 徽章/技能/经历分色类型标签/获奖分区展示）+ 侧边栏「简历」导航（FileUser 图标）
5. **pom**：core 增加 pdfbox 3.0.3（版本号收敛在 backend/pom.xml properties）

## 改动原因

匹配 Agent（W2 后续）需要结构化的候选人画像作为匹配输入的一极（另一极是 JobRequirements）。简历是用户数据入口，必须先于匹配上线。

## 技术概念卡

### PDFBox 文本提取
- 是什么：Apache PDFBox 的 `PDFTextStripper` 抽取 PDF「文字层」；3.x 加载入口从 `PDDocument.load` 迁移到 `Loader.loadPDF`（本切片踩到并修复）
- 项目里哪里用了：`ResumeService.extractText`；扫描件（图片型 PDF）抽不出文字层 → 空串 → 降级 pending，可走 reparse/人工
- 面试可能追问：PDF 解析为什么难？（PDF 是排版格式而非文档格式——文字按绘制指令散布，无段落语义；扫描件本质是图片需 OCR/多模态）

### multipart 文件上传
- 是什么：HTTP `multipart/form-data` 编码，Spring 用 `MultipartFile` 接收；前端 `FormData` 由浏览器自动生成带 boundary 的 Content-Type
- 项目里哪里用了：`POST /api/resumes`；前端 `uploadResume` **不走统一 request()**——它会强设 `Content-Type: application/json` 破坏 boundary
- 面试可能追问：Spring 默认上传上限多少？（1MB，`spring.servlet.multipart.max-file-size` 调整）；魔数校验 vs 扩展名校验（文件头 `%PDF-` 不可伪造，扩展名可以）

### JSONB 半结构化存储
- 是什么：PostgreSQL 二进制 JSON 列，支持索引/查询但无固定 schema
- 项目里哪里用了：`resumes.parsed` 存 ResumeProfile——结构会随匹配 Agent 演进（加字段），JSONB 免去每次写迁移；实体侧 `String` + `@JdbcTypeCode(SqlTypes.JSON)`
- 面试可能追问：为什么不拆关系表？（写多读少、结构演进快、总是一整份读写——反范式的合理场景）；代价？（失去数据库级约束与 join 能力，校验责任上移到应用层）

### 上传成功 + 解析可失败的分离设计
- 是什么：用户动作（上传）必须成功，增值能力（AI 解析）允许失败补偿（reparse）
- 项目里哪里用了：`ResumeService.upload` 中 `parseAndFill` 任何失败仅记日志，parsed 留空 → `parse_status=pending`
- 面试可能追问：为什么不放 MQ 异步解析？（单用户本地应用，同步 3s 内可接受；架构匹配规模，不过度设计——但接口留了 reparse 作为补偿入口）
