## 改动内容

W2 第四切片：匹配 Agent v1（LLM 精评 + 24h 缓存 + 详情页报告展示）。

1. **core 层**：
   - `MatchDetail` record（agent-design §3.3 schema：hardChecks 硬性条件逐条核对 → hardPass → scoreTotal/breakdown → 技能对照 → highlights → suggestion → oneLiner；**字段顺序即 CoT 顺序**，先论证后结论）
   - `LlmService.evaluateMatch(jobHeader, jdText, resumeProfileJson)`：system（资深校招顾问 + 评分基准 + 军工所特化硬条件）+ user（岗位信息 + JD 截断 3000 字 + ResumeProfile JSON）双段 prompt；**失败重试 1 次**（附上次错误让模型自我修正）；task=`match_eval` 记账
   - `MatchingService`：404/422 前置校验（无默认简历、简历未解析、JD 为空各有明确引导文案）→ **24h 缓存**（同 job+resume 复用最新报告）→ LLM 精评 → **服务端规则兜底**（hardPass=false 强制总分 ≤39 并重建 detail，钳制 0-100）→ 落库（model_used + prompt_version=`match-v1` 供效果回溯）
2. **API**：`POST /api/match/jobs/{id}`（可指定 resume_id，缺省默认简历）、`GET /api/match/jobs/{id}`（最新报告，无则 404）；`JobDetail.latest_match_report` 从 null 占位变为实填
3. **前端**：`MatchReportCard` 组件（分数锚点配色 ≥85 绿/70-84 蓝/55-69 琥珀/<55 灰、硬性条件 ✓/✗ 逐条、三维分进度条、技能对照徽章、契合亮点、投递建议、模型与 prompt 版本元信息）替换详情页占位卡；生成/重新评估按钮（同步 3-10s loading）

**与设计文档的偏差**：Stage 1 pgvector 粗筛未做——它服务于「每日推荐管线从大量岗位粗筛 Top 20」的规模场景（W3），单岗位按需匹配没有粗筛需求，且 embedding 依赖 DashScope 额度（暂不可用）。v1 直接 LLM 精评，粗筛随 W3 发现引擎上线。

## 改动原因

匹配报告是 W2 验收的核心交付（「对 5 个岗位出匹配报告」），也是简历项目叙事的关键一环（Agent 双阶段设计 + prompt 工程 + 输出校验）。

## 技术概念卡

### CoT 字段顺序（先论证后结论）
- 是什么：结构化输出中把「证据字段」（hardChecks）放在「结论字段」（scoreTotal）之前，利用 LLM 自回归特性让打分建立在已输出的核对结果上
- 项目里哪里用了：`MatchDetail` 字段顺序 + prompt 中「先输出 hard_checks 再打分」的显式要求
- 面试可能追问：为什么有效？（自回归模型生成后面的 token 时以前面内容为条件——先写核对过程，结论自然受其约束；反之先给分数，模型会「合理化」硬门槛）

### 不信任模型的规则遵守度（服务端兜底）
- 是什么：prompt 里写了「hardPass=false → 总分 ≤39」，模型仍可能违反（实测 job3：hard_pass=false 但按维度给出 35+30+10=75）；落库前服务端强制封顶
- 项目里哪里用了：`MatchingService.enforceScoreRules`，并用修正后的分数**重建 MatchDetail** 保证 JSONB 与 score_total 列一致
- 面试可能追问：LLM 输出能直接落库吗？（不能——校验、钳制、业务规则重写都在服务端；prompt 是「约定」不是「约束」）

### LLM 结果缓存（成本与体验）
- 是什么：同 (job_id, resume_id) 24h 内复用最新报告（cached=true 标记），重复查看零成本零延迟
- 项目里哪里用了：`MatchingService.match` 前置缓存查询；失效策略 = 时间窗 + 简历换新档案后 resume_id 变化
- 面试可能追问：缓存键怎么选 / 何时失效？（精评是最贵调用——长 prompt；输入快照未版本化时用时间窗兜底，避免「简历改了报告没变」的永久脏缓存）

### system/user 双段 prompt
- 是什么：system 放角色与规则（稳定、可缓存），user 放当次输入（岗位 + JD + 简历）
- 项目里哪里用了：`evaluateMatch`（前几个解析任务是单段 user prompt，匹配是首个双段——角色扮演类任务的惯例）
- 面试可能追问：为什么分开？（关注点分离：规则迭代不动数据装配；部分供应商对 system 有 prompt 缓存优化）
