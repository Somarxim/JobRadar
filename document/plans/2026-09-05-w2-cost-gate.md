## 改动内容

W2 收尾切片：LLM 每日 token 成本闸（匹配 Agent 上线前的既定防线）。

1. `LlmUsageRepository.sumTokensSince(since)`：聚合查询今日累计 token（`coalesce(sum,0)`，失败行 token 为 null 自动跳过）
2. `LlmService.overBudget(task, model)`：所有 4 个 LLM 任务入口（jd_parse/poster_parse/resume_parse/match_eval）统一过闸——超闸拒发 + 记失败账（error 含用量明细 `used/limit`），返回 Optional.empty 走各调用方既有降级路径（422 人工兜底）
3. 配置：`jobradar.llm.daily-token-limit`（默认 200000，环境变量 `LLM_DAILY_TOKEN_LIMIT` 覆盖，置空字符串=不限）；「今日」按服务器本地时区零点切

## 改动原因

匹配 Agent 已上线（每次精评数千 token），开发记录里连续两片标记「成本闸上线前补」。DeepSeek 按 token 计费，无闸的定时管线/批量操作可能一夜烧穿余额。

## 技术概念卡

### 成本闸（Rate/Budget Limiting）
- 是什么：按时间窗聚合历史用量，超限拒发——与限流（rate limit）同族，但闸门维度是「钱」而非「QPS」
- 项目里哪里用了：`LlmService.overBudget` 作为所有 LLM 任务的统一前置闸（单一事实来源，调用方零感知）
- 面试可能追问：闸放在哪一层？（入口统一闸 vs 每调用方各自判断——前者不漏；更精细可加分任务配额）；超闸后用户体验？（降级到人工路径 + 失败账可查，不是硬崩）

### 聚合查询的 nil 处理
- 是什么：JPQL `sum()` 对空集返回 null，`coalesce(sum(x), 0)` 兜底；可空列被 sum 自动跳过
- 项目里哪里用了：`sumTokensSince`（失败行 total_tokens 为 null，不计入成本——合理，失败调用通常不计费）
- 面试可能追问：为什么不用 count 估算？（各任务 token 量级差 10 倍以上——海报 ~4k vs JD ~0.5k，按次数估不准）
